Terminal Workspace · versión pública depurada

Una base clara para seguir desarrollando

Una aplicación nativa experimental para trabajar con terminales, archivos y paneles mediante una navegación inspirada en Neovim. Este repositorio permite revisar el desarrollo sin publicar datos de la máquina de origen.

Alcance de esta publicación. La historia Git pública comienza con una instantánea depurada. La cronología enumera las etapas y referencias locales hasta el 6 de noviembre de 2026, pero los commits históricos originales no están publicados. El código de esta rama base corresponde a una instantánea anterior a parte del trabajo de navegación; ese trabajo se presentará por separado para revisión.

Qué contiene

  • Crates Rust, prototipo Swift, dependencias vendorizadas y recursos necesarios seleccionados.
  • Configuración de proyectos de ejemplo: no enumera rutas personales.
  • Una cronología depurada con fecha y referencia local de cada commit inventariado.

Se excluyeron capturas, logs, recibos locales, documentación interna y dos scripts con rutas específicas de la máquina. La exportación no sustituye un análisis de seguridad completo.

Estado y límites

El proyecto sigue en desarrollo. No se declara equivalencia completa con Neovim ni funcionamiento continuo certificado. La instantánea pública y sus cambios requieren verificaciones propias; el último paquete instalado en el entorno de origen puede ser diferente.

En esta etapa están suspendidos los tests automatizados. La cronología recoge títulos de commits, no la evidencia detallada de sus verificaciones.

Operación

El workspace Rust se define en Cargo.toml. El proyecto usa un runtime y scripts de build para macOS; sus supuestos y dependencias necesitan adaptarse al entorno público. Antes de instalar o reemplazar una app, verificar el artefacto exacto y conservar los datos del usuario.

Los scripts que asumen recursos o rutas locales omitidos no deben considerarse portables solo por estar presentes. La guía se ampliará al verificar el flujo público de compilación e instalación.

Política de cambios

Usar una rama por objetivo, describir el comportamiento observable y sus límites, y presentar los cambios en un PR. No afirmar que un cambio quedó integrado o instalado hasta comprobarlo. La documentación y el video de cada PR deben corresponder a su base y HEAD.
